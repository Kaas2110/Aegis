# Aegis: следующие магазины после RuStore

Актуализация 19 октября 2026 года. Первый приоритет — богатые модели, локальное приложение и подготовка RuStore (`rustore-release.md`). Публикации, новые аккаунты, покупки и платёжные договоры не выполнялись.

## Общая архитектура

Сохраняем React Native / Expo, общие API, модельные контракты, учёт и серверные ключи. Магазинные идентификаторы, подпись, канал, push и платежи задаются отдельно. Секреты в клиент не копируются. Для разных магазинов не нужны отдельные модели и базы.

## Раздельная проверка политик

Нельзя переносить утверждение «18+ достаточно» между магазинами. Допустимость коэффициентов, прогнозов и вспомогательных функций оценивается по конкретным правилам и фактическому поведению приложения.

Google Play ограничивает приложения, помогающие делать ставки реальными деньгами, в том числе вспомогательные функции с коэффициентами/результатами и управлением ставками вне разрешённых категорий. Отсутствие приёма денег в Aegis не означает автоматического одобрения. Перед работой нужна проверка точного scope по [официальной политике](https://support.google.com/googleplay/android-developer/answer/18258653?hl=ru).

Для App Store и AppGallery требуется новая проверка актуальных официальных правил, анкет, регистрации и денежных расчётов. Старые значения комиссий, возраста, обязательных тестеров, сроков ревью и выплат из прежнего черновика здесь не подтверждаются и не используются как условия реализации.

Не скрывать функциональность при модерации. Если канал требует другого продуктового состава, решение должно быть явным, соответствовать правилам и быть согласовано с владельцем; одного удалённого флага недостаточно для заявления о соответствии.

## Отдельный магазинный проект

1. Зафиксировать функции, географию и бесплатный/платный scope.
2. Сверить правила магазина, аккаунта/подписи/сборки, сохранить ссылки и дату.
3. Определить applicationId, стратегию подписи/обновлений и сборочный профиль.
4. Проверить публичные URL политики, удаления и поддержки, раскрытие данных и права на контент.
5. При утверждённых подписках/push спроектировать SDK и серверный учёт, затем протестировать. Поле тарифа в БД не означает работающий billing.
6. Проверить конкретный пакет, подготовить честную карточку и инструкции ревью.
7. Отправлять только после отдельной команды владельца.

Политика, согласие, экспорт и удаление аккаунта уже реализованы в Aegis. Проверять работу и публичную доступность нужно; создавать дубли по старым TODO — нет.
