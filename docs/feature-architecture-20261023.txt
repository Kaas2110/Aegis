0. ОБЯЗАТЕЛЬНЫЙ ПОРЯДОК
Сначала Steam/источники, причинная архитектура и полный каталог признаков. Затем техническая приёмка. Обучение, HPO, ablation и оценка качества моделей сейчас остановлены. Разрешены проверки правильности кода, временных соединений, сохранённых данных и воспроизводимости. Наличие 38 468 колонок не означает, что все они заполнены или уже подаются в публичную модель.

1. ОДИН ЛОГИЧЕСКИЙ ГЕНЕРАТОР ПРИЗНАКОВ, НЕ ОДНА МОДЕЛЬ НА ВСЕ СЛУЧАИ
Источник -> неизменяемое исходное наблюдение -> типизированное нормализованное состояние -> исторический контекст по ссылке -> общие чистые преобразования признаков -> вектор конкретной версии схемы -> модель соответствующей фазы/цели -> журнал -> API/UI.
Python и TypeScript не должны независимо переизобретать формулы. Канонические преобразования выдаются одним версионированным producer; обучение потребляет сохранённые векторы того же producer. Если отдельный язык требуется по производительности, равенство реализации доказывается golden/parity тестами; расхождение блокирует использование схемы.
Схема содержит упорядоченные stable names, типы, единицы, формулы, маски, версии источника/producer, schema hash. Модель объявляет ожидаемую схему, фазу, target и допустимые профили. Нельзя молча отрезать/добавлять/переставлять колонки. Вектор с несовпадающим hash не попадает в inference.
Текущие frozenPlayerContext, playerHeroEconomyFeatures, roshanFeatures и steamFeatureBundle — части этой архитектуры. Старые PredictionModel, C1/C2 и research builders пока отдельные пути, а не законченная общая система.

2. ИСТОРИЯ И LIVE — ДВА РАЗНЫХ ВХОДА ОДНОГО ПРОГНОЗА
Исторический snapshot содержит только прошлые завершённые карты: форму игроков/команды, показатели выбранных героев, player×hero, пары/контрпики, стиль, мету, распределения длительности/убийств и доступные native hero-minute нормы. Он загружается из нашей БД, а не повторным запросом провайдерам по открытию карточки.
Динамический observation содержит состояние ТЕКУЩЕЙ карты: часы, стороны/герои/игроки, счёт, native NW/GPM/XPM/уровни/предметы/объекты и Roshan, только когда эти поля действительно получены. Поля одного пакета не подменяются более новыми полями другого endpoint.
Генератор соединяет static snapshot + один coherent dynamic packet + допустимый префикс предыдущих packets той же карты и профиля. Смена профиля/карты, откат часов, конфликт идентичности сбрасывают соответствующие динамические окна. История героя не превращается в якобы наблюдаемый текущий предмет, GPM или роль.
Сохранение исторического контекста на карту не означает вшивание текущей формы в веса модели. Веса меняются при обучении; значения исторических признаков выбираются при прогнозе и затем используются повторно на этой карте.

3. ТРИ РАЗНЫХ ВРЕМЕНИ И ДВА РЕЖИМА ДОКАЗАТЕЛЬСТВ
eventTime/gameClock: к какому игровому состоянию относится факт.
receivedAt/availableAt: когда этот факт действительно был получен/доступен нашей системе.
computedAt/ingestedAt: когда запись обработана или занесена в новый журнал. Поздний импорт не меняет исходный receivedAt.
Отдельно alignmentAnnotationKnownAt: когда мы позднее узнали метаданные для проверки соответствия старого снимка карте/минуте. Это не предиктор.
Для фактически записанного прогноза все входные факты должны быть доступны не позже decisionAt. Для исторического обучения нельзя подмешивать итог текущей карты в её ранний вектор. Outcome текущей карты присоединяется отдельно как label, после формирования features.
Поздняя аннотация старта или длительности может валидировать исторический срез, но не передвигать cutoff истории, не открывать поздние составы и не становиться входом модели. Итоговая длительность, применённая для контроля принадлежности кадра, не используется в признаке remaining time или в выборе удобных кадров без отчёта о selection bias.
Различать recorded и reconstructed cohorts. История из старого архива без прежних receipts может дать ретроспективно восстановленный датасет с явной политикой доступности; она не доказывает, что приложение выдало такой прогноз в тот день. end + 300 секунд — предположение конкретного протокола, не реальный receipt. Метрики разных режимов не объединять в одно подтверждение production parity.

4. ФИКСАЦИЯ КОНТЕКСТА СРАЗУ ПОСЛЕ ДРАФТА
Для будущего online пути политика freeze = first_complete_draft_receipt: первый сохранённый полный драфт с подтверждённой идентичностью карты/сторон/героев. Не требовать поздно публикуемого официального start_time ради статического postdraft-прогноза.
Создать отдельный observed_draft контракт. Он не подделывает phase = 5, не создаёт нулевой live GPM и не ослабляет guard native economy. Если первый драфт наблюдался уже посреди игры, помечать late_first_observation; не приписывать этому snapshot существование на нулевой минуте.
historyCutoffAt равен времени указанного зафиксированного триггера; в snapshot попадают лишь допустимые прошлые карты с доступными outcome/необходимыми полями до cutoff. Текущая карта исключается всегда. Выбранный герой/current roster разрешаются по времени наблюдения драфта; их личная история берётся отдельно из прошлых карт.
В offline replay использовать тот же реально записанный триггер и cutoff. Если его нет, строить отдельную reconstruction-policy, например actual-start-frozen, с отдельным названием и доказательствами. Не смешивать её незаметно с first_complete_draft_receipt. Драфт впервые замеченный на 20-й минуте не входит в postdraft/0-minute когорту; статическая схема сама по себе не делает позднее наблюдение прематчевым.
Пока доступен лишь частичный roster, hero/team признаки могут быть известны, а player-specific признаки остаются missing. Полный драфт — десять подтверждённых выбранных героев, а не обязательно десять открытых account_id. Отдельно проверять допустимость состава для конкретной схемы модели.

5. НЕИЗМЕНЯЕМЫЙ CACHE И ХРАНЕНИЕ
Ввести append-only history_context_snapshots: id/contentHash, matchId, draftHash, rosterHash, sideIdentityHash, cutoffPolicy/historyCutoffAt, availabilityBasis, producerVersion, schemaHash, sourceSnapshotHash, patchEvidenceHash, generatedAt, значения/маски/support/provenance. Learned-преобразования дополнительно связываются с learnedTransformStateSha256 и TRAIN/fold/cohort binding; одинаковая схема с разными обученными состояниями не является одним ключом. Уникальный ключ по всей идентичности снимка; конкурентные одинаковые запросы используют одну committed запись.
Ссылка historyContextRef неизменяема в журнале прогноза. Обновление общей истории после окончания другой карты не переписывает контекст уже рассчитанной текущей карты.
Официальное исправление игрока/героя создаёт новую версию контекста, validFromObservationId и причину; не заменяет старые прогнозы задним числом. Если полный hero draft зафиксирован в t0, а account раскрыт в t1, история новой версии остаётся as-of t0, identity действует лишь с t1. Допустим новый экспорт недостающей истории с доказательством availableAt <= t0 и новым sourceSnapshotHash. Нельзя расширить историческое окно до t1 или заполнить player-признаки прежних кадров задним числом. Конфликт без доказательства приостанавливает зависимые family, не назначает случайный ID.
Для исторических исходных фактов хранить версии по observed/available time. Текущие materialized hero_stats/player_hero_stats/player_ratings/team_form не являются историческим хранилищем; их нельзя join-ить к прошлым датам без версии.
Snapshots/labels/raw сохраняются раздельно по назначению, соединяются по устойчивому mapId и явным временам. Источник live и postmatch/backfill не определяется одним названием таблицы. Не перезаписывать raw live кадр итоговым postmatch состоянием.

6. ИДЕНТИЧНОСТЬ И ПРЕДОТВРАЩЕНИЕ РАССИНХРОНИЗАЦИИ
Связь игрока: accountId + heroId + side + подтверждённый teamId, с отдельными missing правилами. Позиция в массиве и экономический ранг не равны роли 1–5.
Без подтверждённого accountId допустима история героя; форма конкретного игрока неизвестна. Не сопоставлять только по никнейму.
Сравнение текущего героя с историческим hero×minute профилем использует тот же показатель/единицы. Native GPM, earned gold и net worth — три разных величины. Нельзя заполнять отсутствующий NW из gold_t или GPM=NW/min.
Справочники героев/предметов/правил версионируются. Patch включает буквенную ревизию; calendar assignment хранится с основанием и uncertainty, не выдаётся за подтверждение от провайдера.
Задержка между двумя Steam endpoint — не задержка от реального события. recorded receipt freshness и end-to-end delay — разные измерения. Обновление каждые несколько секунд не доказывает отсутствие задержки трансляции.

7. ИНДИВИДУАЛЬНАЯ СИЛА, МЕТА И СОЧЕТАНИЯ
Сохранять богатые текущие группы, не урезая их из-за слабой общей корреляции: player/player×hero/player×team/player×team×hero; hero-population performance residuals; comfort/recency/support; формы за 7/30/90 дней; team style/opponent style response; hero pairs/counters; late tendency отдельно для team/player/hero/player×hero; form×trajectory×hero×minute.
Добавить условные связи ally-player pair, playerA×heroA×allyPlayerB, playerA×heroA×allyHeroB, точная пара playerA×heroA×playerB×heroB. Для редких сочетаний сохранять count/effectiveCount/uncertainty и отсутствующее значение; не выдавать победы в двух картах за устойчивую силу.
Raw WR, сглаженная WR и lift относительно индивидуального baseline — отдельные признаки. Любой learned baseline/target encoding/словарь наиболее частых пар для эксперимента строится внутри TRAIN-fold; итог holdout не участвует. Сглаживание/приоры описываются формулой и версией, не выбираются по красивой test метрике.
Командный профиль должен сохранять распределение десяти игроков/пяти на сторону, роли при доказательстве, слабые/сильные позиции, концентрацию ресурсов и взаимодействия. Единственная сумма условной силы не заменяет исходные группы. Отдельный latent strength допустим только как явно обученный OOF-признак, не как произвольная формула, объявленная истиной.
Мета: hero pick/ban/win trends по явным population, patch/subpatch, окнам, стороне/роли, support. Pro и Immortal pubs не смешиваются как одна популяция. Популярность героя и winrate не равны причинной силе.

8. ROSHAN И TOTALS
Держать отдельно raw timer, доказанную семантику таймера, inferred bounds и подтверждённые события. Нулевой таймер не означает Roshan alive. Время от смерти вычисляется только от известного события или маркированной оценки; countdown неизвестного смысла не становится точным временем до возрождения.
Семейства: жив/мёртв/неизвестно, time-since-death, earliest/latest respawn, Aegis holder/side/lifetime/consumption/snatch при наблюдении, ordinal Roshan kill, относительно преимущества/силы carry/объектов/исторической скорости завершения. Сравнение по герою и игроку — отдельные условные профили.
Прематч/последрафт total models предсказывают распределение итоговых kills/time без выдуманного текущего состояния. Live models — распределение оставшихся kills/time; текущий счёт/время прибавляются ровно один раз. На всех линиях вероятности берутся из одного согласованного CDF/survival, а не из независимых случайных чисел.
Собственные линии генерируются вокруг текущего распределения. При выбранной БК используются её актуальные линии/правила settlement, наши вероятности вычисляются на этих линиях; коэффициент БК не является вероятностью модели. Обработать pPush/атомы/правый хвост и единицы секунды→минуты один раз.

9. МОДЕЛИ И ВЫВОД НА ЭКРАН
До драфта: prematch карта/серия и prematch totals с доступной историей. После полного драфта: postdraft outcome/totals немедленно по статике. Во время игры: live winner/totals по coherent snapshot. Окончание карты/серии: фактический результат, не прогноз завершённого события.
Главная карточка ВСЕГДА показывает победителя всего матча/серии. До начала — prematch series. После появления полного драфта, во время игры и между картами — contextual series: общий богатый набор признаков текущей карты, замороженная историческая форма игроков/героев/команд, BO1/BO3/BO5, счёт серии, подробности уже завершённых карт, устойчивость после поражения и доступные сведения о драфте/стилевых взаимодействиях. Внутри карточки — победитель выбранной/текущей карты и её totals по убийствам и длительности. Не сводить series model к арифметике только score+map probability. Прогноз карты может быть дополнительным входом с OOF/временной защитой и версией происхождения; он не заменяет общий богатый контекст. Команда может проигрывать текущую карту, оставаясь фаворитом всей серии. Нельзя копировать map win probability в series probability для BO3/5; для BO1 событие совпадает по определению.
Контекстная модель серии должна работать и без активного live-пакета между картами: использовать известный счёт и доступные итоги предыдущих карт, а не сохранять их динамику как состояние следующей карты. При полном новом драфте обновлять series прогноз сразу, не ожидая первой минуты. Логические режимы не предрешают количество отдельных обученных моделей: общую контекстную модель и экспертов по фазе/счёту сравним позднее. UI/API проверяются по target, seriesId, mapId, формату и счёту; одинаковое поле probability без идентичности события недопустимо.
Переключение карт уже частично реализовано; сейчас интерфейс не переделывать. При входе в карточку автоматически открывается текущая карта с её прогнозами. Пользователь может выбрать предыдущую сыгранную карту в пределах формата BO1/BO3/BO5 и увидеть именно её героев и фактические результаты. При подключении новых моделей сохранить это поведение и не сбрасывать ручной выбор прошлой карты при каждом live-обновлении. Текущий прогноз не показывается как прогноз выбранной прошлой карты; если отдельно показывается история прогнозов, она берётся из сохранённого журнала и явно обозначается. Завершённое событие по умолчанию показывает фактический результат.
Неизвестный драфт следующей карты не заполняется героями текущей. Итог и performance предыдущих карт серии допустимы только после их реальной доступности. Историческая оценка защищает всю серию/компоненту от попадания в TRAIN и test одновременно.
Будущие эксперименты сравнят одну модель с minute+interactions и фазовые experts на одинаковых splits/checkpoints. После 80 минут — единая поздняя группа. Больше времени означает больше наблюдаемой истории, но не автоматически более точную модель. Сейчас эти эксперименты не запускаются.

10. PRODUCTION ПРИЁМКА СТЫКА
Prediction journal обязан хранить observation/raw/context/schema/model hashes, значения и missing masks, cutoff policy/basis, actual receipt и game clock, phase/profile, map/series IDs и причину недоступности. Детали доступны диагностике; UI при отказе пишет «Прогноз недоступен».
Тесты инвариантов: future append не меняет прошлый vector; изменение label не меняет features; переупорядочение игроков не меняет смысл; late correction не переписывает snapshot; неизвестная роль/identity не придумывается; вектор другой версии не обслуживается; после restart тот же snapshot ref даёт тот же vector; одновременно 100 читателей не запускают 100 запросов к поставщикам; stale/rewound packets не заменяют новое состояние.
Проверять API path, а не только чистый helper. Один trace должен прослеживаться от collector receipt до model input и отображённого результата. Новые широкие кандидаты сначала shadow/diagnostic; публичный допуск требует отдельной проверки качества/полноты/свежести и не включается этим документом.
Требование 95% относится к реально доступным своевременным входам для заявленного профиля и cohort. Знаменатель включает ожидавшиеся наблюдения/пропуски, не только успешные ответы. Структурные нули hero one-hot не увеличивают покрытие. Sparse historical support отличается от отсутствия live поля; правила missing/backoff каждого family явные, broad catalogue не урезается скрытно.

11. ИСТОЧНИКИ И ГРАНИЦЫ РЕШЕНИЯ
Основной проектный путь: прошлые факты из своей БД (OpenDota и другие подтверждённые исторические источники), текущая динамика одним согласованным Steam-профилем. Это решение о разделении обязанностей, а не заявление, что Steam уже доказал все поля и своевременность.
STRATZ не обязателен для нового Steam+history bundle. Сохранить старые данные, ключ и остановку по 403; не выключать legacy producers вслепую и не подменять их популяцию. Долги fallback/meta/synergy описаны отдельным review.
Для GLG без phase не записывать phase = 5 по условию clock > 0. Offline annotation допускается отдельным контрактом после identity/profile/time проверки; публичный phase admission имеет собственные доказательства. Необъяснённые absent/zero clocks остаются различными состояниями.
Нерешённые эмпирические факты: реально своевременная joint coverage; долговременное покрытие native history; точный смысл/полнота Roshan fields; абсолютный lag относительно события. Они проверяются техническими source pilots, а не обучением моделей с оптимистичными предположениями.

12. GITHUB / GRAPHIFY
PR1 по source sync слит с явным разрешением владельца: main 74bed2e50acb19587883f6144e747f18773d4648. Graphify должен подтвердить именно новый commit; queued не означает ready.
Каноническая локальная рабочая версия — APP вместе с сохранённой точкой продолжения текущего блока. Один PR создаётся на законченный блок работ, а не на каждую отдельную правку. На существенных промежуточных этапах сохранять локальные исходники и checkpoint, без автоматического обновления облака. По завершении блока выполнить source inventory, secret/runtime exclusion и проверки, затем создать PR либо обновить уже открытый PR этого блока. БД/raw/weights/ключи не являются частью source parity.
Parity проверяется по манифесту Git tree и фактическому содержимому APP; CRLF/LF явно отделяются от смысловых отличий. Generated Android/build outputs требуют воспроизводимой генерации из source plugins, не слепой публикации локальных artifacts.
Graphify retrieval использует только явно подтверждённый snapshot. Во время выполнения блока main и граф могут отставать; это отмечается явно, а локальные исходники, diff и checkpoint остаются первичными. После отдельно разрешённого merge законченного блока дождаться новой индексации, проверить новые символы и обновить reviewed memory. Синхронизация на каждую правку не требуется. Новый репозиторий/удаление старого не нужны для этого процесса.
